Capitolo 1. Primo avvio e setup rapido

Obiettivi didattici
  • Configurare una scansione iniziale stabile e ripetibile.
  • Bilanciare velocita e accuratezza usando THREADS/PORT RANGE.
  • Produrre un report baseline di riferimento.
  1. Apri Anibus e verifica lo stato Ready.
  2. Inserisci TARGET: hostname, IP o URL.
  3. Imposta PORT RANGE e THREADS.
  4. Abilita JavaScript Analysis e SQL Injection Testing quando necessario.
  5. Premi Start Scan.
Esercizio guidato

Esegui due run sullo stesso target con THREADS 20 e 60. Confronta stabilita, completezza e rumore nel log.

Capitolo 15. Guida amministratore (deployment, profili, hardening)

15.1 Modello di deployment

Distribuire Anibus su workstation controllate, separate da sessioni amministrative di produzione.

15.2 Profili operativi

ProfiloObiettivoImpostazioni consigliate
DevIterazione rapidaRange ridotto, thread medi, log estesi
StageValidazione pre-produzioneRange medio, export rigoroso, proxy opzionale
Audit ProdAssessment autorizzatoThread conservativi, finestre pianificate
  • Dev: cicli veloci e output verbose.
  • Stage: validazione pre-produzione con policy di export rigorosa.
  • Audit Prod: thread conservativi e finestre pianificate.

15.3 Hardening

  • Account least-privilege.
  • Controllo delle rotte in uscita.
  • Protezione delle cartelle history/report.
  • Tracciabilita di autorizzazioni e artefatti.

15.4 Policy proxy

  • Preferire pool validati e selettore stabile.
  • Usare Auto transport solo con endpoint onion locali autorizzati.
  • Monitorare streak di errore e quarantena route.

15.5 Governance operativa

Separare ruoli operatore/revisore/approvatore e conservare i report in archivio immutabile.

Case Study: Gap di governance

Prima

Difficile ricostruire ownership e autorizzazioni delle esecuzioni.

Errori tipici

  • Account condivisi.
  • Report senza riferimento ticket.
  • Retention non immutabile.

Analisi soluzione

Ruoli separati e catena di approvazione tracciata hanno eliminato i gap di audit.

Capitolo 16. Cookbook (playbook pronti)

Metodo di studio

Scegli un playbook per obiettivo, segui tutti i passaggi e modifica un solo parametro alla volta.

Playbook 1: Mappatura superficie esterna

  1. Target pubblico, range 1-4096, thread 20-40.
  2. Esegui scan base + WHOIS + TLS audit.
  3. Esporta baseline e marca servizi critici.

Playbook 2: Snapshot rischio web

  1. Abilita JS Analysis e SQL Testing.
  2. Lancia controlli XSS, CORS, JWT, GraphQL.
  3. Ordina risultati per confidenza e impatto.

Playbook 3: Operativita proxy resiliente

  1. Carica pool da file e aggiorna con harvesting.
  2. Abilita Auto transport e verifica endpoint onion.
  3. Ruota chain su instabilita ripetuta.

Playbook 4: Drift monitor schedulato

  1. Abilita scheduler nella finestra approvata.
  2. Confronta snapshot con Diff Mode.
  3. Escalation solo per differenze persistenti.

Playbook 5: Supporto triage incident

  1. Riduci scope al perimetro incidente.
  2. Esegui check rapidi e confronto storico.
  3. Esporta report sintetico per SOC.
Case Study: Triage accelerato

Prima

Triage lento per uso sistematico di scansioni complete.

Errori tipici

  • Nessuna riduzione del perimetro iniziale.
  • Output incident e baseline mischiati.
  • Template handoff assente.

Analisi soluzione

Playbook con scope ristretto e report breve ha ridotto tempi e rumore decisionale.

  • Avanzato: SQL-to-DB extraction e SourceMap exploit context.
