Chapter 1. First Launch and Quick Start

This chapter gives a straight path from opening the app to producing your first reportable output.

Learning goals
  • Understand which parameters affect scan reliability most.
  • Launch a first run with controlled risk of false negatives.
  • Capture a clean baseline report for later comparison.
  1. Open Anibus and verify the status line shows Ready.
  2. Enter target in TARGET (hostname, IP, or URL).
  3. Set PORT RANGE (for first run, use a focused interval).
  4. Set THREADS based on link stability (10-30 for unstable networks).
  5. Enable JavaScript Analysis and SQL Injection Testing if needed.
  6. Press Start Scan and monitor stream output in Scan Results.
Hands-on exercise

Run two scans against the same target: one with 20 threads and one with 80. Compare runtime, missing services, and output noise. Keep the more stable profile as your baseline preset.

  3. Use Rotate on failures.

  • Other onion: extra local onion-compatible endpoint.

Case Study: Proxy Route Stabilization

Before

Frequent timeouts, noisy results, unstable route quality under regional restrictions.

Typical mistakes

  • Too many threads for low-quality routes.
  • No fallback chain policy.
  • No quarantine awareness.

Solution review

Switch to stable selector, enable transport auto with verified local endpoints, reduce thread pressure, and rotate on recurring failures.

Chapter 15. Administrator Guide (Deployment, Profiles, Hardening)

15.1 Deployment model

Deploy Anibus as a controlled desktop utility in segmented analyst workstations. Keep execution context isolated from production admin credentials and privileged management sessions.

15.2 Environment profiles

ProfileGoalRecommended defaults
DevFast iterationLow port range, moderate threads, verbose logs
StagePre-production verificationMedium range, strict export discipline, proxy optional
Prod AuditControlled authorized assessmentConservative threads, scheduled windows, change tracking

15.3 Hardening checklist

  • Run under least-privilege OS account.
  • Constrain outbound routes through approved gateways where required.
  • Keep local history/report folders access-restricted.
  • Version-lock and verify runtime dependencies.
  • Use explicit scan authorization tickets and retained evidence trail.

15.4 Proxy hardening policy

  • Prefer validated pools and stable selector mode.
  • Enable transport auto only with approved local onion endpoints.
  • Monitor failure streaks and quarantine events.
  • Avoid permanent reliance on single-country routes.

15.5 Operational governance

Define role boundaries: operator, reviewer, approver. Store exported reports in a signed and immutable archive when possible.

Case Study: Audit Governance Drift

Before

Reports were exported inconsistently and scan scope approvals were not traceable.

Typical mistakes

  • Shared operator accounts.
  • Missing approval ticket references.
  • No immutable archive policy.

Solution review

Role separation, mandatory scope ticket linkage, and signed export retention eliminated audit gaps.

Chapter 16. Cookbook (Ready-to-Run Playbooks)

How to use this chapter

Choose one playbook by objective, execute steps exactly, then adapt only one variable at a time (threads, range, transport, or checks). This keeps your evidence comparable between runs.

Playbook 1: Fast External Surface Mapping

  1. Target: public host/IP, port range 1-4096, threads 20-40.
  2. Run base scan, WHOIS, TLS audit, HTTP protocol detect.
  3. Export baseline report and mark critical open services.

Playbook 2: Web Stack Risk Snapshot

  1. Enable JS Analysis + SQL testing.
  2. Run XSS, CORS, JWT, GraphQL checks.
  3. Prioritize findings by confidence and exploitability hints.

Playbook 3: Resilient Proxy Route Operation

  1. Load pool from cache, then refresh with harvesting.
  2. Enable Auto transport, verify onion endpoints in log.
  3. Rotate on instability and maintain chain fallback.

Playbook 4: Scheduled Drift Monitoring

  1. Set scheduler ON for controlled scan window.
  2. Track port/service deltas via diff and history.
  3. Escalate only persistent changes across multiple cycles.

Playbook 5: Incident Triage Support

  1. Narrow target scope to incident perimeter.
  2. Run rapid checks and compare with previous snapshots.
  3. Export concise report for SOC handoff.
Case Study: Incident Triage Acceleration

Before

Triage took too long because teams ran full-scope checks for every event.

Typical mistakes

  • No perimeter-first scope reduction.
  • Mixing baseline and incident outputs.
  • No fixed handoff template for SOC.

Solution review

Playbook-driven narrowed scope, snapshot comparison, and concise export template reduced response time.

Глава 15. Руководство администратора (развертывание, профили, hardening)

15.1 Модель развертывания

Развертывайте Anibus на контролируемых рабочих станциях аналитиков, изолированных от production-админских сессий.

15.2 Профили эксплуатации

ПрофильЦельРекомендуемые настройки
DevБыстрая итерацияУзкий диапазон, средние потоки, подробные логи
StageПредпрод проверкаСредний диапазон, строгая дисциплина экспорта
Prod AuditКонтролируемый аудитКонсервативные потоки, плановые окна

15.3 Hardening checklist

  • Запуск под least-privilege учетной записью.
  • Контроль outbound маршрутов и egress-политик.
  • Защита каталогов history/report и артефактов экспорта.
  • Регламент хранения результатов и журналов.
  • Версионирование профилей и формальные approval-процедуры.

15.4 Proxy hardening policy

  • Предпочтение стабильному селектору и проверенному пулу.
  • Карантин проблемных направлений и ротация цепочек.
  • Периодическая ревалидация cache-пула.

15.5 Операционная дисциплина

Разделите роли оператор/ревьюер/аппрувер, фиксируйте scope и сохраняйте артефакты в неизменяемом хранилище.

Кейс: Провал в аудите из-за process gaps

До

Невозможно доказать, кто и в каком scope запускал проверки.

Типовые ошибки

  • Общие учетные записи.
  • Отчеты без ticket-связки.
  • Нефиксируемое хранилище артефактов.

Разбор решения

Ролевая модель, обязательная привязка к заявке и неизменяемый архив закрывают audit gaps.

Глава 16. Cookbook (готовые playbook-сценарии)

Как работать с playbook

Выбирайте сценарий по задаче, выполняйте шаги без пропусков и меняйте за итерацию только один параметр. Так результаты остаются сопоставимыми.

Playbook 1: Быстрая карта внешней поверхности

  1. Диапазон 1-4096, потоки 20-40.
  2. Скан + WHOIS + TLS + HTTP protocol detect.
  3. Экспорт baseline-отчета.

Playbook 2: Web risk snapshot

  1. Включить JS Analysis и SQL Testing.
  2. Запустить XSS/CORS/JWT/GraphQL набор.
  3. Сортировать по confidence/priority и экспортировать.

Playbook 3: Устойчивый proxy режим

  1. Load from file + Start Harvesting refresh.
  2. Transport Auto и проверка логов endpoint availability.
  3. Rotate/failover на сбоях, обновление цепочки.

Playbook 4: Плановый drift monitoring

  1. Включить scheduler в допустимое окно.
  2. Сравнивать snapshots через Diff Mode.
  3. Эскалировать только устойчивые изменения.

Playbook 5: Incident triage support

  1. Сузить scope до incident perimeter.
  2. Провести быстрый пакет проверок.
  3. Сформировать короткий отчет для SOC handoff.
Кейс: Ускорение incident triage

До

На каждое событие запускался полный сценарий, что увеличивало время реакции.

Типовые ошибки

  • Нет первичного сужения периметра.
  • Смешение baseline и incident данных.
  • Неформализованный handoff в SOC.

Разбор решения

Жесткий playbook с коротким шаблоном отчета позволяет ускорить handoff без потери качества.

Глава 17. Полный каталог реализованных функций (по TODO + коду)

Эта глава описывает, что уже реализовано в программе и как этим пользоваться в реальном рабочем потоке. Используйте ее как «операторскую карту» перед запуском сканов.

17.1 Архитектура и качество (уже сделано)

  • Dependency Injection: сервисы подключаются через приложение, а не создаются хаотично в контроллере.
  • Unit-тесты: SQL payload/cms-профили, ScanDiffService, LeakInfo priority/placeholders.
  • Integration-тест: ScanCoordinator + стратегия сканирования на localhost.
  • Checkstyle в Maven: единый стиль и контроль качества кода.
Как использовать на практике

Перед релизом запускайте compile/test pipeline и проверяйте, что новые фичи не ломают базовые сценарии сканирования и экспортов.

17.2 Кнопки Scan Results: что подключено и как запускать

  • UDP Scan: кнопка запускает UDP-проверку доступности сервисов.
  • Subdomain: перечисление поддоменов и проверка кандидатов.
  • Source Map: анализ .map и извлечение контекста исходников.
  • Param Miner: поиск скрытых GET/POST параметров canary-методом.
  • Diff Mode: сравнение текущего и предыдущего среза.
  • Scheduler Start/Stop: периодические сканы с накоплением истории.
Порядок запуска

Сначала базовый Start Scan, затем точечные кнопки анализа из Scan Results, в конце Diff/Export и фиксация результата в истории.

17.3 Анализ и обнаружение: полный список реализованного

  • Passive Recon Mode: title/headers/robots/sitemap/favicon hash без активных payload.
  • Secrets Validation: проверка форматов ключей (AWS/GitHub/Stripe/Telegram/Slack/Google) без внешней отправки.
  • Аутентифицированный краулинг JS-анализа: login/cookie/session сценарии.
  • API Security Mode: авто-детект OpenAPI/Swagger и прогон endpoint из схем.
  • LeakInfo confidence (HIGH/MEDIUM/LOW) + отображение в анализе.
  • Risk scoring: Severity × Exploitability × Exposure.
  • Curl-сниппеты для найденных endpoint.
  • XSS detector (reflected), SSRF detector, XXE detector.
  • CORS Misconfiguration checker.
  • Directory Bruteforce (wordlist + HEAD + группировка по статусам).
  • JWT Analyzer (decode, alg none, expired, weak HMAC).
  • GraphQL Introspection scanner.
  • Subdomain Takeover checker (dangling DNS signatures).
  • SourceMap Exploit Context Analyzer: категория атаки, нарратив, рекомендация, ссылки на CVE/OWASP.

17.4 Сеть и инфраструктура: полный список реализованного

  • Security Drift Scheduler: алерт при изменении открытых портов между сканами.
  • Network Topology Map: граф hop-to-hop по traceroute во вкладке Topology.
  • WHOIS Lookup: двухэтапный IANA -> авторитативный whois.
  • SSL/TLS Deep Audit: протоколы, cipher suite, цепочка сертификатов, SAN, expiry.
  • DNS Zone Transfer (AXFR): raw TCP/53 и парсинг записей.
  • HTTP/2 + HTTP/3 detection: ALPN + Alt-Svc.
  • WebSocket Detector: проверка upgrade на типовых путях.
  • ASN Lookup: определение автономной системы по IP.
  • IPv6 Scan support в HostResolver (корректная обработка IPv6 адресов).

17.5 Уязвимости и CVE: полный список реализованного

  • CVE Severity Indicator: CRITICAL/HIGH/MEDIUM/LOW.
  • Exploit-DB PoC links по CVE.
  • Log4Shell checker (CVE-2021-44228).
  • Spring4Shell checker (CVE-2022-22965).
  • Heartbleed checker (OpenSSL heartbeat профиль).
  • Расширенный VulnerabilityScanner fingerprint (включая IIS/GitLab/EOL сигналы).

17.6 UI, экспорт и операционная продуктивность

  • Proxy Chain Visual Manager: drag-and-drop построение цепочки.
  • Export HTML report: styled html + JS фильтр.
  • Export PDF: через встроенный pipeline печати/рендера.
  • Statistics dashboard: распределения портов/сервисов/рисков.
  • Scan Results live filter (поиск по тексту в реальном времени).
  • История сканов: autosave, просмотр, сравнение, повторный запуск.
  • Keyboard shortcuts: F5, Escape, Ctrl+S, Ctrl+L, Ctrl+F.
  • Theme switcher Dark/Light.
  • Notifications по завершению скана.
  • SQL-to-DB Extraction: UNION/ORDER BY probes для метаданных БД.
Кейс: Полный рабочий цикл оператора (все реализованные блоки)

До

Команда запускала только базовый скан и теряла ценность реализованных модулей (API, CVE, Topology, Diff, History).

Типовые ошибки

  • Не использовать кнопки Scan Results после базового прогона.
  • Не включать JS/API security ветку для web-target.
  • Не фиксировать baseline и не сравнивать через Diff/History.

Разбор решения

Стандартизируйте runbook: Start Scan -> Scan Results actions -> Security/CVE checks -> Topology/Statistics -> Export HTML/PDF -> History/Diff. Так используется весь реализованный функционал из TODO.
